# Обобщенное описание проекта: Информационная система автосалона

Данный документ представляет собой структурированное обобщение поэтапного курсового проекта по разработке backend-части информационной системы для мультибрендового автосалона.

---

## 1. Общая суть проекта
Разработка backend-системы, проходящей 5 этапов эволюции. На каждом этапе добавляется новый слой технологий и архитектурных решений, при этом **бизнес-логика, заложенная в начале, не упрощается и не нарушается**, а адаптируется под новые технологические реалии.

---

## 2. Предметная область (Бизнес-логика)

### Роли пользователей
* **USER (Клиент)**: просмотр авто, конфигуратор, оформление заказа/тест-драйва, просмотр и отмена *только своих* заказов.
* **MANAGER (Менеджер)**: просмотр всех заказов, управление тест-драйвами, служебные операции над заказами.
* **WAREHOUSE_ADMIN (Администратор склада)**: управление каталогом, остатками, согласование заказов, управление внутренними складскими процессами.
* **ADMIN (Системный администратор)**: полный доступ ко всем эндпоинтам и сущностям системы без ограничений.

### Ключевые сущности
* **Автомобиль** и **Запчасть**.
* **Заказ на покупку автомобиля в наличии**.
* **Заказ на автомобиль с определенной комплектацией** (с конфигуратором).
* **Заявка на тест-драйв**.
* **Заказ на сборку** (внутренняя складская сущность, введенная в ЛР4).

### Ключевая бизнес-фича: Конфигуратор автомобилей
* Позволяет заменять базовые узлы (колеса, руль, интерьер и т.д.) на совместимые альтернативы с пересчетом итоговой стоимости.
* **Строгая валидация**: проверка совместимости выбранного узла с конкретной моделью автомобиля и проверка наличия всех обязательных узлов в конфигурации.

### Жизненный цикл заказа
Строгий набор статусов (от «Оформлен» до «Завершен» или «Отменен») с переходами, зависящими от действий склада, менеджера и факта оплаты.

## 3. Эволюция архитектуры (по лабораторным работам)

### Лабораторная работа 1: Фундамент (Domain & Core)
* **Фокус**: система сборки Gradle.
* **Результат**: Спроектированная доменная модель, бизнес-логика конфигуратора, предметные исключения и валидации без привязки к фреймворкам.

### Лабораторная работа 2: Web и Данные (Monolith Spring Boot)
* **Фокус**: Spring Boot, PostgreSQL, REST API, интеграционное тестирование.
* **Результат**: Трехслойная архитектура (Integration → Service → Persistence). 
  - Использование DTO (MapStruct/ModelMapper), запрет на проброс JPA-сущностей наружу.
  - Миграции БД (Liquibase), реализация Soft Delete (`removed` флаг).
  - Фильтрация данных через Spring Data Specifications.
  - Документация API через Swagger/OpenAPI.

### Лабораторная работа 3: Безопасность (Security & Auth)
* **Фокус**: Spring Security, Keycloak, RBAC (Role-Based Access Control).
* **Результат**: 
  - Все REST-эндпоинты защищены.
  - Реализована проверка прав на уровне методов (`@PreAuthorize`).
  - Клиент (USER) видит и управляет *только своими* заказами (проверка OwnerId).
  - Keycloak развернут и управляется через Docker.

### Лабораторная работа 4: Распределенная система (Microservices & Async)
* **Фокус**: Декомпозиция, Брокер сообщений (Kafka/RabbitMQ), Event-Driven Architecture.
* **Результат**: Система разделена на два автономных микросервиса:
  1. **OrderService**: Работа с клиентами, заказами, тест-драйвами, публикация доменных событий.
  2. **StorageService**: Каталог, запчасти, складские остатки, внутренняя сущность «Заказ на сборку».
* **Паттерны**: Асинхронное взаимодействие при смене статуса заказа на «Оплачен», **Outbox Pattern** для гарантированной доставки событий и атомарности транзакций, сквозное логирование (traceId).

### Лабораторная работа 5: Синхронная связь и отказоустойчивость (gRPC)
* **Фокус**: gRPC, межсервисные вызовы, resilience.
* **Результат**: 
  - `StorageService` поднимает gRPC-сервер для отдачи списка авто в наличии.
  - `OrderService` выступает gRPC-клиентом, проксируя эти данные через свои REST-эндпоинты (`GET /api/v1/cars` и `GET /api/v1/cars/{id}`).
  - Реализована обработка таймаутов и возврат `503 Service Unavailable` при недоступности склада.

---

## 4. Ключевые архитектурные требования и паттерны

1. **Строгое разделение слоев**: Никаких JPA-сущностей в REST-ответах. Взаимодействие исключительно через DTO.
2. **Base Entity**: Все сущности наследуют базовый класс с полями: `UUID id`, `Instant createdAt`, `Instant updatedAt`, `boolean removed` (Soft Delete).
3. **Атомарность событий**: Изменение статуса в БД и отправка события в брокер должны происходить атомарно (реализация Outbox Pattern).
4. **Идемпотентность**: Обработка сообщений из брокера должна быть идемпотентной.
5. **Инфраструктура как код**: Весь стек (БД, Keycloak, Брокер, Микросервисы) должен подниматься одной командой через `docker-compose`.
6. **Покрытие тестами**: Обязательные интеграционные тесты с автоматическим поднятием зависимостей через Testcontainers.
